Two layers, on purpose

SHEET 01/11

The framework that runs tests and the system that writes them don't know about each other — and shouldn't.

LayerWhat it isStatus
ExecutionPlaywright + TypeScript: POM, Allure, logging, smoke/regression gate, SauceLabs. Runs tests, no AI involved, no app hardcoded.Already built — README.md
AuthoringClaude Code skills + Playwright MCP + subagents. Writes the tests the execution layer runs, using domain knowledge supplied per project (Sheet 09).This document

Every file the authoring layer produces follows the execution layer's own conventions — setPage(), comFunc logging, POM structure, testdata/*.json. It never invents a new pattern; it copies the one already there. Neither layer hardcodes an app — both take it as configuration.

The pipeline

SHEET 02/11

Steps 0–1 run inline, in this thread. Steps 2–3 are separate subagent calls — the boundary that keeps this cheap.

  1. Step 0 — Resolve input. Scenario text, a TC-ID, or blank (pull next unimplemented TC). Not browser-observable? Stop and redirect to Unit/API.
  2. Step 1 — Classify, inline. Formalize into a TC block, classify the layer in one line, grep (not read) for reuse.
  3. Step 2 — Build, delegated. Write the Page Object + spec + config entry, verify selectors against the real page via Playwright MCP, run it, debug up to 3 times.
  4. Step 3 — Review, delegated. Best-practices checklist against the new file(s) only.
  5. Step 4 — Fix, once. Only if Step 3 found a [CRITICAL] issue.
  6. Step 5 — Report, inline. TC-ID, files, pass/fail, score — under 10 lines.
Guard rail Step 1 checks whether app-domain is still the shipped-empty template before writing anything. A scenario generated against an empty domain skill is a guess dressed up as a test — the pipeline stops and asks you to fill it in first (Sheet 09) rather than produce that.

Why subagents

SHEET 03/11

Run everything in one long conversation and the tenth scenario of the day pays for the reading done by the first nine.

Each subagent reads app-domain, playwright-best-practices, and the one closest existing spec/PO it needs, does its work — including the multi-round MCP debug loop, which can be the most expensive part of a run — and returns a short summary. None of that working context ever enters this orchestrator thread.

Named, tool-restricted agents — not just a generic spawn Steps 2 and 3 run as test-builder and test-reviewer (.claude/agents/*.md), not the built-in general-purpose type. What matters: test-reviewer's tool list has no Edit and no Bash — it is structurally incapable of modifying what it reviews, not just instructed not to. "Review proposes, it doesn't silently rewrite" is enforced at the tool-permission layer for this role, not only in the prompt. test-builder has no Agent tool, so the chain stays flat — two hops, never a tree of subagents spawning further subagents.

Self-healing locators

SHEET 05/11

Selector rot is the highest-frequency maintenance cost in any real Playwright suite — this is the pipeline's answer to it.

generate-tests' Step 5 debug loop routes locator-class failures (timeout waiting for an element, element not found, strict-mode violation) to the heal-test skill instead of guessing-and-retrying the same selector:

  1. Read the failure's trace (trace: "retain-on-failure" in playwright.config.ts) — the exact DOM at the moment of failure, no re-navigation needed.
  2. Re-locate the element by the old locator's purpose, not its literal string — preferring a new stable identifier, then role + accessible name, then label/placeholder text, then visible text — never downgrading to a bare positional selector.
  3. Judge confidence, then act.
ConfidenceAction
High — one unambiguous matchApply, re-run to confirm, log it
Medium — text/label or position-disambiguated matchApply, re-run to confirm, log it, flag for a human glance
Low — multiple candidates or nothing serves the same purposeApply nothing — cross-check app-domain; this may be an app bug, not selector rot
No silent fixes Every applied fix — High or Medium — gets one row in docs/reports/healing-log.md (spec/PO, old locator, new locator, confidence, reason). A bad auto-heal needs to be traceable, not discovered by accident. Low confidence never auto-applies, on purpose.

heal-test is also callable standalone (/heal-test <spec>) against a previously-passing spec that starts failing later, independent of the authoring pipeline — the maintenance use case, not just the authoring-time one.

Model & token levers

SHEET 06/11

MCP wiring

SHEET 07/11

.vscode/mcp.json only talks to VS Code's own MCP client. Claude Code needed its own registration.

{
  "mcpServers": {
    "playwright": {
      "command": "npx",
      "args": ["@playwright/mcp@latest", "--headed"]
    }
  }
}
// .mcp.json — project root, git-shareable

First use in a new terminal approves this project's MCP server once. Drop --headed for unattended/CI runs.

MCP discipline One snapshot per page to build the selector map, verify only the elements this scenario touches, then write the Page Object from that. Re-snapshotting the full accessibility tree after every single action is the most common way an MCP-driven build burns tokens for no benefit.

Bootstrapping a new project

SHEET 09/11

Everything on Sheets 01–08 is inert until this is done — nothing in the repo points at an app until you point it.

  1. Copy .env.example → .env, set BASE_URL (+ APP_USER/APP_PASSWORD if the app has a login).
  2. Fill in every section of .claude/skills/app-domain/SKILL.md — app overview, user flows, business rules, data models. Every skill in Sheet 04 reads this file first; the guard rail on Sheet 02 checks it's no longer empty.
  3. Login flow → adapt the selectors already marked for editing in loginLogout.ts and auth/example.setup.ts. No login → delete the auth/ setup pair and its project entry in playwright.config.ts.
  4. Replace home-po.ts and example.spec.ts with your first real page/spec, or keep them as the smoke-test baseline.
  5. Run /ship-test <a scenario describing the app's first flow> and let the pipeline (Sheet 02) take it from there.

The same checklist lives in CLAUDE.md, which Claude Code reads automatically at session start — this copy is here so this document stays self-contained.

CI & CD

SHEET 10/11

Everything through Sheet 09 runs when a human types a command. This is what runs on its own — CI on every push, plus a CD gate an app's release pipeline can call.

push (any branch)  ─▶ FULL   ─┐
pull_request       ─▶ smoke  ─┼─▶ test (windows-latest) ─┬─▶ HTML report artifacts
schedule 03:00 UTC ─▶ smoke  ─┤                          └─▶ publish-report (Pages, opt-in)
workflow_dispatch  ─▶ either ─┘
                              lint-skills · quality (lint + typecheck)
                              review (changed specs → PR comment, AI, optional)
  • test is deterministic — npm run pw:test[:smoke], nothing AI about it, runs regardless of secrets. Runs on windows-latest on purpose: the logging path (C:\LogFolder\...) and Allure teardown are Windows-specific by design (Sheet 07) — this matches local dev rather than working around it.
  • Push runs the FULL suite deliberately — the code you just pushed is exercised together with every test already in the repo, so a new spec cannot pass in isolation while quietly breaking an existing one. PRs get smoke for speed; the daily smoke catches app-side drift on days nobody pushed.
  • The failure signal is the artifact, not a bot. Every run uploads the Playwright HTML report, which embeds the trace, screenshot and error for each failing test. A red run is diagnosable from the artifact alone, with no AI vendor configured anywhere and nothing commenting on your behalf.
  • review (optional, AI) runs review-tests against exactly the spec/PO files changed in the PR — the same file-scoping discipline as Sheet 08 — and posts the result as a PR comment.
  • The CD half — e2e-gate.yml lets an application's release pipeline call this suite as a promotion gate between deploying staging and promoting production, with per-environment secrets from GitHub Environments. See docs/cicd.md.
Never a silent gate review needs ANTHROPIC_API_KEY as a repo secret — missing it skips the job cleanly rather than failing the build, and the HTML report artifact is there either way. Note that secrets is not a context GitHub allows in a job-level if: — referencing it there makes the entire workflow file fail to parse — so a small config job resolves it where env is legal and review gates on that output. review also runs the Claude Code invocation with continue-on-error: true: an AI job that fails to run is a missed comment, never a red PR check by itself. The same "CI auto-comments, it doesn't auto-merge" guardrail from docs/roadmap.md applies at the workflow level, not just in the skill instructions.

Driving from Copilot

SHEET 11/11

Nothing through Sheet 10 requires Claude Code specifically except the .claude/skills/* file format and the two claude -p calls in CI. This is what makes that explicit for a second driver.

One process, two drivers. The two knowledge files (app-domain, playwright-best-practices) and the seven pipeline-stage process definitions stay exactly where they are, in .claude/skills/*/SKILL.md — that's Claude Code's own auto-discovery folder, so moving them would break its pipeline for no benefit. Every Copilot-facing file added for this is a thin pointer at those same definitions, not a rewrite:

.github/copilot-instructions.md          →  repo-wide, mirrors CLAUDE.md
.github/instructions/*.instructions.md   →  path-scoped conventions (specs, page objects)
.github/prompts/<name>.prompt.md  ──────▶  "Follow .claude/skills/<name>/SKILL.md" + Copilot-specific mechanics

One *.prompt.md per pipeline stage, invoked as /name in Copilot Chat's Agent mode — same commands, same file outputs, same conventions as the Claude Code skills they point at. Edit the process once, in .claude/skills/, and both tools follow the update; a prompt file that duplicated the content instead would drift the moment either copy got edited without the other.

Real-browser verification works from either driver because it was already wired for both: .mcp.json registers Playwright MCP for Claude Code, .vscode/mcp.json registers the same server for VS Code's own MCP client — Copilot's Agent mode already had tool access before any file in this section existed.

Where the parity isn't perfect ship-test's Build and Review steps run as isolated Claude Code subagents for the context-isolation reasons in Sheet 03 — that mechanism has no direct Copilot equivalent as of this writing. Driven from Copilot, the same five steps run sequentially in one chat instead; the process and file outputs are identical, the token-isolation benefit just doesn't apply to that path yet.

GitHub's Copilot coding agent (assign-to-@copilot on an issue) is a real option for picking up a failure you have filed by hand — but it's issue-driven and asynchronous, not a scriptable "run this step in this job" call the way claude -p is, so it's a manual assignment, not automated in the workflow.
