## Architecture Analysis

**AACargo Facilities page characteristics:**
- Server-rendered / static HTML — no login required
- Facility data fetched from backend at page load (not a JS SPA with client API)
- No forms that submit data (search redirects via URL `/AACargo/ua/facilities/DFW`)
- No Unit-testable pure functions in scope (all content is display logic)
- No interceptable JSON API (page renders facility data server-side)

**Decision Impact:**
> Since this is a **read-only content display flow** with URL-based navigation and no client-side business logic to unit test, the **vast majority are E2E**.
> Anti-pattern alert: do NOT push these to Unit/API — there is nothing to unit test here. The value is in verifying the UI renders correct data from the live system.

## Decision Rationale — Contested Assignments

**Why TC-202 (invalid code) is E2E not Unit:**
> The validation happens server-side (URL routing at `/AACargo/ua/facilities/INVALID`).
> No client-side function to unit test. Browser must navigate to verify graceful error handling.

**Why TC-301 (empty search) is E2E not Unit:**
> The search form submit is browser navigation. No JS validator to isolate. E2E needed.

**Why TC-103/TC-104 are E2E not Component:**
> Drop-off times and weather are server-rendered sections. No React/Angular component to test in isolation. Content validation requires full page load.
